# pgschema2toon development plan

## Goal

Evolve `pgschema2toon` from a PostgreSQL-specific proof of concept into a database-neutral schema extraction and TOON rendering tool while preserving the current CLI behavior.

## Current limitations

- PostgreSQL catalog extraction lives in `cmd/pg2toon/main.go`.
- The TOON converter receives PostgreSQL-shaped JSON instead of a canonical schema model.
- Foreign keys are parsed from `pg_get_constraintdef()` text.
- Only the `public` schema and ordinary tables are included.
- Defaults, generated expressions, identity metadata, unique/check constraints, and referential actions are not represented structurally.
- Nested catalog aggregates are not explicitly ordered.
- Output file errors are ignored.
- Automated coverage is limited.

## Target architecture

```text
Database-specific catalogs
          |
          v
Database extractor adapter
          |
          v
Canonical schema model
          |
          v
Database-independent TOON encoder
```

Suggested packages:

```text
cmd/pg2toon/
    main.go

internal/database/
    extractor.go
    factory.go
    postgres/
        extractor.go
        queries.go

pkg/schema/
    model.go

pkg/toon/
    encoder.go
    encoder_test.go
```

- Timestamp type normalization
- Stable table ordering

## Phase 2: Canonical schema model

Introduce structured types that do not depend on PostgreSQL output strings.

```go
type Database struct {
    Schemas []Schema
}

type Schema struct {
    Name   string
    Tables []Table
}

type Table struct {
    Schema      string
    Name        string
    Comment     string
    Columns     []Column
    PrimaryKey  *PrimaryKey
    ForeignKeys []ForeignKey
    Uniques     []UniqueConstraint
    Checks      []CheckConstraint
    Indexes     []Index
}
```

Important rules:

- Preserve native database types.
- Optionally expose normalized type families.
- Preserve ordered local and referenced column lists.
- Store referential actions structurally.
- Keep constraints separate from indexes, even when the database implements a constraint with a backing index.
- Define escaping rules for identifiers and multiline comments.

## Phase 3: PostgreSQL adapter

- Move catalog access out of the CLI.
- Extract foreign-key columns from `pg_constraint.conkey` and `confkey` instead of parsing SQL text.
- Extract defaults with `pg_get_expr(ad.adbin, ad.adrelid)`.
- Extract identity and generated-column metadata.
- Include unique, check, exclusion, and primary-key constraints.
- Support schema selection.
- Include partitioned tables where requested.
- Represent partial and expression indexes structurally.
- Add adapter conformance tests against the Testcontainers fixture.

## Phase 4: Database-independent TOON encoder

- Accept the canonical schema model rather than raw JSON.
- Write to `io.Writer`.
- Preserve the current PostgreSQL output where possible.
- Add output for defaults, unique/check constraints, composite relationships, and referential actions.
- Add golden tests for escaping and deterministic output.

## Phase 5: Additional databases

Recommended order:

1. SQLite, to expose assumptions around schemas, comments, and type affinity.
2. MySQL/MariaDB, using `information_schema` plus vendor-specific metadata.
3. SQL Server, using `sys.*` catalogs and extended properties.
4. Oracle, if required.

Each adapter must pass a shared conformance suite and publish its capabilities.

## Pull request strategy

1. **Integration coverage:** comprehensive PostgreSQL Testcontainers fixture.
2. **PostgreSQL correctness:** deterministic extraction, structured foreign keys, defaults, and constraints.
3. **Database abstraction:** canonical model and extractor interface.
4. **TOON encoder refactor:** database-independent rendering and golden tests.
5. **SQLite adapter.**
6. **MySQL adapter.**

Keeping these changes separated makes review easier and prevents the abstraction work from hiding PostgreSQL correctness regressions.
